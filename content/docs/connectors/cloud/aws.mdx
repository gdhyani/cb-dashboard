---
title: AWS / S3-compatible
description: Use S3, Cloudflare R2 or other S3-compatible storage with the AWS SDK, presigned URLs included, without the real access keys.
---

Store your real AWS access key pair in cb once. Every developer's app gets stand-in AWS keys and a local endpoint.
The AWS SDK signs each request with the stand-in keys as usual; the cb gateway checks the signature's access key,
re-signs the request with the real keys, and sends it to the real endpoint. Presigned URLs are re-signed the same
way when they are opened.

## Before you start

- You are an owner or admin of the organization.
- You have a real access key ID (`AKIA…`) and secret access key, and the region your buckets live in.
- For Cloudflare R2, MinIO, Backblaze or other S3-compatible storage, you have the storage's S3 endpoint, for
  example `https://<account>.r2.cloudflarestorage.com`.
- Developers who will run the app have [access](/docs/guides/dashboard/access) to the environment.

<Callout type="tip">
  Give cb an access key scoped to what the app needs. **Save & test** lists buckets, so the key also needs
  permission to list buckets on that endpoint.
</Callout>

## Add it in the dashboard

<Steps>
<Step>
### Open the Variables tab

Open your project, pick the environment, and go to the [Variables tab](/docs/guides/dashboard/variables). Click
**AWS S3** in the **Quick add** row, or click **Add variable** and set **What is this?** to **AWS / S3-compatible**.
The dialog is titled **Add AWS / S3-compatible variable**.
</Step>
<Step>
### Name the key and paste the real values

Type the **Key** for the secret key, usually `AWS_SECRET_ACCESS_KEY`, and paste the real secret into **Secret access
key**. Enter the real **Access key ID** (cb needs it to sign requests) and the **Region**.
</Step>
<Step>
### Choose the extra keys

Open **Suggested extra keys**. `AWS_ACCESS_KEY_ID` is ticked already, because AWS SDKs need it. Tick `AWS_REGION`
if your code reads the region, and `AWS_ENDPOINT_URL` to hand your app the local endpoint.
</Step>
<Step>
### Set a custom endpoint for R2 and other storage

For anything other than AWS S3, open **Advanced** and set **Custom endpoint**. For Cloudflare R2, use
`https://<account-id>.r2.cloudflarestorage.com` and the region `auto`. Without a custom endpoint, cb uses
`https://s3.<region>.amazonaws.com`.
</Step>
<Step>
### Save & test

Click **Save & test**. cb sends a signed `ListBuckets` request to the endpoint with the real keys before saving.
If it is rejected, nothing is saved and the dialog shows the error.
</Step>
</Steps>

## Use it in code

Create the client from the environment as you do in production. Pass the endpoint explicitly (recent AWS SDK
versions also read `AWS_ENDPOINT_URL` on their own) and use path-style addressing, because the local endpoint is
an IP address that can't carry a bucket name as a subdomain.

<Tabs items={["S3", "Presigned URLs", "SES", "SQS"]}>
<Tab value="S3">
```ts title="lib/storage.ts"
import { GetObjectCommand, PutObjectCommand, S3Client } from "@aws-sdk/client-s3";

export const s3 = new S3Client({
  region: process.env.AWS_REGION,
  endpoint: process.env.AWS_ENDPOINT_URL,
  forcePathStyle: true,
});

await s3.send(new PutObjectCommand({ Bucket: "uploads", Key: "hello.txt", Body: "hi" }));
const object = await s3.send(new GetObjectCommand({ Bucket: "uploads", Key: "hello.txt" }));
console.log(await object.Body?.transformToString());
```
</Tab>
<Tab value="Presigned URLs">
```ts title="lib/presign.ts"
import { GetObjectCommand } from "@aws-sdk/client-s3";
import { getSignedUrl } from "@aws-sdk/s3-request-presigner";
import { s3 } from "./storage";

const url = await getSignedUrl(s3, new GetObjectCommand({ Bucket: "uploads", Key: "hello.txt" }), {
  expiresIn: 60,
});
// http://127.0.0.1:7409/uploads/hello.txt?X-Amz-Credential=AKIACB…&X-Amz-Signature=…
```

A presigned URL points at the local endpoint and carries the stand-in signature. When it is opened, cb re-signs it
with the real keys. A browser on the same machine can open it while `cb run` is running.
</Tab>
<Tab value="SES">
```ts title="lib/mail.ts"
import { SendEmailCommand, SESClient } from "@aws-sdk/client-ses";

const ses = new SESClient({
  region: process.env.SES_REGION,
  endpoint: process.env.SES_ENDPOINT,
  credentials: {
    accessKeyId: process.env.SES_ACCESS_KEY_ID!,
    secretAccessKey: process.env.SES_SECRET_ACCESS_KEY!,
  },
});

await ses.send(
  new SendEmailCommand({
    Source: "shop@acme.example",
    Destination: { ToAddresses: ["ada@acme.example"] },
    Message: { Subject: { Data: "Hello" }, Body: { Text: { Data: "Hi Ada" } } },
  }),
);
```
</Tab>
<Tab value="SQS">
```ts title="lib/queue.ts"
import { SendMessageCommand, SQSClient } from "@aws-sdk/client-sqs";

const endpoint = process.env.SQS_ENDPOINT!;
const sqs = new SQSClient({
  region: process.env.AWS_REGION,
  endpoint,
  credentials: {
    accessKeyId: process.env.AWS_ACCESS_KEY_ID!,
    secretAccessKey: process.env.AWS_SECRET_ACCESS_KEY!,
  },
});

await sqs.send(new SendMessageCommand({ QueueUrl: `${endpoint}/123456789012/orders`, MessageBody: "hi" }));
```
</Tab>
</Tabs>

<Callout type="note" title="One endpoint per variable">
  Each AWS variable sends every request to one endpoint. cb re-signs for the service and region named in the SDK's
  signature, so SES and SQS work too, but each needs its own AWS variable whose **Custom endpoint** is that
  service's endpoint (for example `https://email.us-east-1.amazonaws.com`). Rename its extra keys to match your code,
  as in the `SES_…` example above.
</Callout>

<Callout type="warning" title="SESv2 reads a different variable">
  AWS SDK v3's `SESv2Client` looks for `AWS_ENDPOINT_URL_SESV2`, not `AWS_ENDPOINT_URL_SES`. If you rely on the
  SDK's environment variables instead of passing `endpoint` in code, name the extra key `AWS_ENDPOINT_URL_SESV2` so
  requests go through cb.
</Callout>

<Callout type="note" title="Beta: SES and SQS">
  S3 is verified end to end with real AWS, including presigned URLs. SES and SQS go through the same signing path
  and are still in beta.
</Callout>

## Run it

```bash
npx cb run -- npm run dev
```

If you ran `cb init`, your package scripts already run under cb. To see the stand-in values, run
`npx cb env print`. See [cb run](/docs/guides/develop/cb-run).

## Limits

- Your app must send requests to the local endpoint; requests straight to `amazonaws.com` are not caught.
- Presigned URLs work only on the developer's machine while `cb run` is running. Don't hand them to other people or
  devices.
- **Save & test** checks keys with an S3 `ListBuckets` request. A key scoped to one bucket still passes ("key
  accepted; can't list buckets"), because AWS checked the signature before refusing the list; an unknown key ID or a
  wrong secret fails. For an endpoint that isn't S3-compatible (SES, SQS), the test can fail even with valid keys. For email, [SMTP](/docs/connectors/cloud/smtp) works with SES SMTP
  credentials.
- Plain `http://` endpoints are accepted only for private addresses, and only while the cb server allows them.
- Revoking a developer's access stops their requests.

## Troubleshooting

| Problem | Fix |
|---|---|
| **Save & test** says "Request rejected (HTTP 403 AccessDenied)" | The real key can't list buckets on this endpoint. Allow it, or check the key and region. |
| **Save & test** says "Request rejected (HTTP 403 SignatureDoesNotMatch)" | The secret access key doesn't match the access key ID. Paste both again. |
| Your app gets `403` with `cb_invalid_credential` ("AWS access key is not valid for this device") | The app signed with keys that aren't this device's stand-ins, for example real keys from a `.env` file or `~/.aws/credentials`. Pass the keys from `process.env`. |
| Requests go to a host like `uploads.127.0.0.1` | The SDK used virtual-hosted addressing. Set `forcePathStyle: true`. |
| Your app gets `502` with `cb_upstream_unreachable` | The cb server couldn't reach the endpoint. Check the **Custom endpoint**. |

More fixes are in [Troubleshooting](/docs/guides/troubleshooting).
