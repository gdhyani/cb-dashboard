description: The env export, typed variable names from cb types, and the @cb/env/register preload.
---

The `@cb/env` package has two entry points your code can use: the `env` object for typed, read-only access to
variables, and the `@cb/env/register` preload that `cb run` loads for you. Neither holds a secret of its own:
`env` only reads what cb put in `process.env`, and those values are [stand-in values](/docs/overview/concepts#stand-in-values).

You don't need either to use cb. Reading `process.env` works the same way. `env` adds compile-time names and a
clear error when a variable is missing.

## Package exports

| Import | Resolves to | Use |
|---|---|---|
| `@cb/env` | `env` (named and default export), types `CbEnv`, `CbEnvAccess` | Server code: typed variable access. |
| `@cb/env` in a browser bundle | A stub that throws at import time | Stops variables reaching client code. |
| `@cb/env/register` | The preload | Loaded by `cb run` through `NODE_OPTIONS`. |

The package needs Node.js 22.14 or newer.

## env

```ts
import { env } from "@cb/env";
// or: import env from "@cb/env";

type CbEnvAccess = { readonly [K in keyof CbEnv]: CbEnv[K] } & {
  get(name: keyof CbEnv | (string & {})): string | undefined;
};

declare const env: CbEnvAccess;
```

`env` is synchronous and returns exactly `process.env[name]`.

### env.NAME

Returns the value of the variable. Names come from `.cb/env.d.ts`, so a typo fails at compile time.

```ts title="lib/db.ts"
import { env } from "@cb/env";
import { Pool } from "pg";

export const pool = new Pool({ connectionString: env.DATABASE_URL });
```

Under `cb run`, reading a name that cb did not provide throws:

```text
cb: DATABASE_URL is not set for this environment. Ask an admin to add it in the dashboard (project → environment → Variables), then restart with "cb run".
```

Outside `cb run` (for example in production, where you set the variables yourself), `env.NAME` behaves like
`process.env.NAME` and returns `undefined` for a missing variable.

### env.get(name)

Returns the value or `undefined`. It never throws, and accepts any string, so use it for optional variables
and names that are not in `.cb/env.d.ts`.

```ts
import { env } from "@cb/env";

const logLevel = env.get("LOG_LEVEL") ?? "info";
```

### Read-only

Assigning to `env` throws `cb: env is read-only. Change values in the dashboard.` `Object.keys(env)` and the
`in` operator reflect `process.env`.

### Server-only

When a bundler resolves `@cb/env` with the `browser` condition, it gets a stub that throws:

```text
@cb/env is server-only: import it in server code (API routes, server components), never in the browser.
```

In Next.js the stub also imports `server-only`, so importing `@cb/env` from a client component fails the build.

## Typed names with cb types

[`cb types`](/docs/reference/cli#cb-types) writes `.cb/env.d.ts` with the variable names of an environment. It
contains names only; values are delivered at run time by `cb run`.

```bash
npx cb types
```

```ts title=".cb/env.d.ts"
// Generated by `cb types` for shop / development. Do not edit; re-run `cb types` after variables change.
// Names only — values are delivered at run time by `cb run`.
export {};

declare module "@cb/env" {
  interface CbEnv {
    readonly DATABASE_URL: string;
    readonly OPENAI_API_KEY: string;
  }
}

declare global {
  namespace NodeJS {
    interface ProcessEnv {
      readonly DATABASE_URL: string;
      readonly OPENAI_API_KEY: string;
    }
  }
}
```

The file adds each name to `CbEnv` (used by `env.NAME`) and to `NodeJS.ProcessEnv`, so `process.env.NAME` is
typed too. Names are sorted, and names that are not valid identifiers are quoted.

<Callout type="note">
  The file must be part of your TypeScript program. If your `tsconfig.json` has an `include` list that doesn't
  cover `.cb/`, add `".cb/env.d.ts"` to it.
</Callout>

`cb types --json` prints `{ "environment": "development", "keys": ["DATABASE_URL", "OPENAI_API_KEY"] }`
instead of writing the file.

## Preload: @cb/env/register

`cb run` and `cb shell` start your command with `NODE_OPTIONS` extended by
`--require <path to @cb/env/register>`, so every Node process they start, including child processes and worker threads, loads the
preload before any of your code runs. You don't import it yourself.

When it loads, the preload:

1. Reads the environment's snapshot from the path in `CB_SNAPSHOT_PATH`. It never makes a network request.
2. Fails closed: if the process wasn't started by `cb run`, or access is revoked, it throws before your app
   code runs.
3. Sets each variable from the snapshot in `process.env`, unless it is already set.
4. Redirects connections to the hosts cb brokers (for example `api.openai.com:443`) to the local agent by
   patching Node's `net`, `tls` and `http2` connections. Other hosts and Unix sockets are not touched, and TLS
   certificate verification stays on.
5. While `cb run` is detecting your app's port, reports the port your app listens on, so
   [webhooks](/docs/guides/webhooks/how-it-works) reach it.

Started without `cb run`, the preload throws:

```text
cb: this process wasn't started with "cb run". Use "npm run dev" (scripts are wired by "cb init") or "cb shell".
```

See [Preload and API](/docs/guides/develop/preload-and-api) for when to use `env` and how the preload fits
your platform.
