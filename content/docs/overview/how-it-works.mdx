cb has three moving parts: the `@cb/env` package on each developer's machine, the cb server (API and gateway)
that holds the real credentials, and the dashboard where admins manage both. This page follows a single
connection from your app to a real service and back, and explains what happens when access is taken away.

<ArchitectureDiagram />

| Part | Runs on | Holds real secrets? | Job |
|---|---|---|---|
| Your app | Developer laptop | Never | Reads `process.env` and uses official SDKs as usual |
| `@cb/env` (CLI, agent, preload) | Developer laptop | Never | Starts your app with stand-in values and pipes its connections to the gateway |
| API and gateway | cb server | Yes, encrypted at rest | Checks access, swaps in the real credential, talks to the real service |
| Dashboard | Browser | Never | Admins add variables, grant access, revoke and audit |

## Stand-in values in your app

When your app starts under cb, its `process.env` holds three kinds of values:

- **Plain values** such as `PORT` or `NEXT_PUBLIC_APP_URL`, exactly as the admin typed them.
- **Stand-in values** for every protected key, such as a database URL or an API key. They have the same shape as
  the real thing, so SDKs accept them, but they are generated by cb for your device and only work through the
  gateway.
- **Personal values** for [random secrets](/docs/overview/concepts#variable) such as `AUTH_SECRET`, generated per
  developer.

A protected database URL, for example, points at your own machine instead of the real database:

## The agent and `cb run`

You start your app with [`cb run`](/docs/guides/develop/cb-run), usually through your existing scripts:
`cb init` rewrites `"dev": "next dev"` to `"dev": "cb run -- next dev"`, so `npm run dev` keeps working.

`cb run` does four things:

1. Makes sure you are logged in and the local **agent** is running (it starts the agent if needed).
2. Makes sure the environment for this project is current on your machine. This file holds only plain values
   and stand-ins.
3. Starts your command with those values merged into its environment, and adds a small preload
   (`@cb/env/register`) through `NODE_OPTIONS`.
4. Forwards output, signals and the exit code, and restarts your app when an admin changes its variables (turn
   this off with `--no-restart`).

The agent is deliberately thin. It listens on `127.0.0.1` only, opens one encrypted WebSocket tunnel to the
gateway per connection, and passes bytes through with your device's identity. It does not understand database
protocols, does not check credentials and never sees a real secret.

## The gateway

The gateway runs inside the cb server. For every tunnel the agent opens, it:

1. **Checks access** in order: your session and device are valid, you are an active member, no
   [emergency stop](/docs/overview/concepts#emergency-stop) covers you, and you have
   [access](/docs/overview/concepts#access) to this service in this environment.
2. **Verifies the stand-in** your app sent: it must be the one issued to your device for this environment and
   service.
3. **Swaps in the real credential**, decrypted only for this use, and connects to the real service. Certificates
   on that upstream connection are always verified.
4. **Records the connection** in the [audit log](/docs/guides/dashboard/audit): who, which device, which service,
   which environment, and the outcome.

Because the real credential is used only on the server, nothing your app can log, dump or intercept contains it.

## Two ways traffic reaches the gateway

<RoutingLayersDiagram />

### Local ports, for databases and URL-based services

When the value in your environment is a URL or a host, cb rewrites it to a local port on your machine. A
PostgreSQL URL becomes `postgresql://cbu_ab12cd34:…@127.0.0.1:7401/app`, an `OPENAI_BASE_URL` becomes
`http://127.0.0.1:<port>/v1`, and so on. Your driver connects to that port, the agent tunnels the bytes, and the
gateway completes the real login upstream.

Agent ports are chosen from `7400`–`7999` and stay the same for each project, so they do not change between runs.

### HTTPS hosts, for APIs with a fixed address

Some SDKs always talk to a fixed host. The Stripe SDK calls `api.stripe.com`, Google sign-in calls
`oauth2.googleapis.com`, and there is no URL in your environment to rewrite. For these, the preload inside your
app redirects connections to those hosts to the agent. The connection is still TLS end to end with certificate
verification on: the gateway presents a certificate for `api.stripe.com` issued by your organization's own
certificate authority, which only processes started by `cb run` trust, and only for these redirected
connections. Nothing is installed on your system and no proxy settings change.

`cb env print` lists both: the values your app sees, and each redirected host with its local port.

## Webhooks

Payment providers can send webhooks to cb's public URL, which checks the real signature and delivers each event,
re-signed with that developer's stand-in secret, to the app that caused it. See
[How webhooks work](/docs/guides/webhooks/how-it-works).

## When access is revoked

Every connection passes through the gateway, so access can be withdrawn at any moment, without rotating a single
key. When an admin removes your access, revokes your device or uses an emergency stop:

- **Open connections close within seconds.** Database clients receive an error in their own protocol:
  `cb: access revoked by admin`.
- **API requests are refused** with HTTP `403` and the body `{ "error": "cb_access_revoked" }`.
- **`cb run` prints a clear message** and leaves your app running, so it can show its own errors.
- **New runs are refused.** `cb run` will not start your app until access is restored.

The stand-in values on the laptop were never usable anywhere else, so there is nothing to clean up. See
[Revoke a device](/docs/guides/admin/revoke-device) and [Emergency stop](/docs/guides/dashboard/emergency-stop).
